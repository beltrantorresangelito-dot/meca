# F1.5 — Sistema formal de migraciones PostgreSQL

Esta fase agrega infraestructura de migraciones. No modifica tablas funcionales de MECA.

## Convención

Cada migración tiene dos archivos:

- `NNNN_nombre.up.sql`
- `NNNN_nombre.down.sql`

Ejemplo futuro:

- `0002_create_quiebres.up.sql`
- `0002_create_quiebres.down.sql`

Nunca modifique una migración que ya fue aplicada en un ambiente. El runner guarda un SHA-256 del archivo y detendrá la ejecución si detecta una modificación posterior.

## Comandos

```powershell
npm run db:status
npm run db:migrate
npm run db:rollback
```

### `npm run db:status`

Solo consulta la tabla de control y muestra migraciones aplicadas/pendientes.

### `npm run db:migrate`

Aplica todas las migraciones pendientes en orden.

Cada migración se ejecuta dentro de una transacción PostgreSQL.

### `npm run db:rollback`

Revierte SOLO la última migración aplicada.

## Tabla de control

El runner crea automáticamente:

`schema_migrations`

Columnas principales:

- version
- name
- filename
- checksum
- applied_at
- execution_ms

Esta tabla es infraestructura; no forma parte del dominio funcional de MECA.

## Seguridad

El runner usa el mismo `models/database.js` y por tanto el mismo `.env` de MECA.

También utiliza `pg_advisory_lock` para impedir que dos procesos de migración se ejecuten al mismo tiempo.

## Primera migración

`0001_meca_v1_baseline` es intencionalmente un NO-OP. Solo marca que el esquema actual corresponde a la baseline previa a MECA Platform.

No crea ni altera tablas funcionales.

## Flujo de prueba recomendado

1. `npm test`
2. `npm run db:status`
3. `npm run db:migrate`
4. `npm run db:status`
5. `npm run db:rollback`
6. `npm run db:status`
7. `npm run db:migrate`
8. `npm run db:status`

El resultado final debe mostrar 0001 como APLICADA.

## Regla de proyecto

Desde F1.5, todo cambio de esquema se entrega como migración versionada. No se aplican cambios estructurales manuales sin registrar su migración correspondiente.
