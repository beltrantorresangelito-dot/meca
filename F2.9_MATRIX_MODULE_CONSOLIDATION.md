# F2.9 — Consolidación formal de MatrixModule

## Motivo del cambio de estrategia

Después de F2.3–F2.8 comprobamos que el patrón Service/Repository funciona,
pero `server.js` seguía por encima de 7.000 líneas.

F2.9 deja de migrar lecturas una por una y consolida las ya validadas dentro
de un módulo vertical formal.

## Nueva estructura

```text
src/modules/matrix/
├── matrix.routes.js
├── matrix.controller.js
├── matrix.service.js
├── matrix.repository.js
└── index.js
```

Flujo:

```text
server.js
   ↓
MatrixRoutes
   ↓
MatrixController
   ↓
MatrixService
   ↓
MatrixRepository
   ↓
PostgreSQL
```

## Lecturas absorbidas

F2.9 centraliza las seis lecturas validadas:

- GET `/api/evaluacion/version-activa`
- GET `/api/matriz/versiones/activa`
- GET `/api/matriz/versiones/por-fecha`
- GET `/api/matriz/versiones/:id/estructura`
- GET `/api/matriz/versiones`
- GET `/api/reglas-evaluacion/version/:id`

Las URLs y contratos HTTP NO cambian.

## Compatibilidad

Los archivos antiguos:

```text
src/modules/domain/legacy-matrix.repository.js
src/modules/domain/legacy-matrix.service.js
```

se convierten en adaptadores mínimos que reexportan MatrixRepository y
MatrixService.

Esto evita romper tests/imports históricos mientras migramos el proyecto.

## Limpieza adicional

Se elimina un segundo handler duplicado de:

`GET /api/reglas-evaluacion/version/:id`

que estaba más abajo en `server.js`.

El primer handler ya capturaba la misma URL y hacía `return`, por lo que el
segundo era código muerto.

## Qué NO cambia

- PostgreSQL
- frontend
- URLs
- POST/PUT/DELETE de matriz
- CRUD administrativo de reglas
- evaluaciones
- audio

## Criterio de aceptación

- `npm test`: 0 fail.
- servidor inicia.
- seis lecturas mantienen sus contratos.
- Supervisor/Auditor sin regresiones.
- `server.js` ya no contiene los seis handlers inline.
- no existe `legacyMatrixService` dentro de `server.js`.
