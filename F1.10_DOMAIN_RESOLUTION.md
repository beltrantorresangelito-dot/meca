# F1.10 — Resolución y consistencia del dominio

## Objetivo

Crear una única forma de resolver:

`Campaña + Fecha -> Quiebre -> Matriz vigente -> Versión vigente`

Esto evita que cada pantalla o endpoint implemente su propia lógica.

## Función PostgreSQL

`resolver_contexto_evaluacion(campana_id, fecha)`

Ejemplo:

```sql
SELECT *
FROM resolver_contexto_evaluacion(1, DATE '2026-08-21');
```

La función:

1. Busca la relación `campana_matriz` activa para la fecha.
2. Exige exactamente una matriz aplicable.
3. Valida implícitamente el mismo Quiebre mediante las relaciones.
4. Selecciona la versión de matriz con `fecha_vigencia` más reciente que no sea posterior a la fecha objetivo.

## Servicio Node

Se agrega:

`scripts/domain/evaluation-context.js`

con:

- `resolveEvaluationContext`
- `validateDomainConsistency`

Todavía NO se conecta `server.js` a este servicio. F1.10 prepara la frontera de dominio; la integración vendrá al iniciar modularización backend.

## Validaciones de consistencia

`validateDomainConsistency()` comprueba:

- campañas sin Quiebre;
- versiones sin Matriz;
- asociaciones Campaña-Matriz entre Quiebres distintos;
- campañas sin una matriz activa.

## Verificación directa

Tomar un `campana.id` real:

```sql
SELECT id, codigo FROM campanas ORDER BY id;
```

Luego:

```sql
SELECT *
FROM resolver_contexto_evaluacion(<ID_CAMPAÑA>, CURRENT_DATE);
```

Debe devolver exactamente una fila.

## Prueba histórica

Usar una fecha antigua:

```sql
SELECT *
FROM resolver_contexto_evaluacion(<ID_CAMPAÑA>, DATE '2025-01-01');
```

Con la asociación inicial desde 1900 debería seguir resolviendo correctamente la matriz histórica actual, siempre que exista una versión con `fecha_vigencia <= 2025-01-01`.

## Casos de error esperados

- campaña sin matriz vigente -> excepción;
- más de una matriz vigente -> excepción;
- no existe versión de matriz con vigencia anterior/igual a fecha -> 0 filas, lo que deberá tratarse en servicio/API.
