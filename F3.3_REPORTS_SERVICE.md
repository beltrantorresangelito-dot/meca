# F3.3 — ReportsService

## Objetivo

Extraer del `server.js` la lógica de transformación de Reportes sin mover
todavía sus rutas HTTP.

Arquitectura:

```text
server.js
   ↓
ReportsService
   ↓
ReportsRepository
   ↓
PostgreSQL
```

## Lógica movida al Service

- KPIs / Ranking;
- construcción de meses disponibles;
- Evolutivo;
- Top fallas;
- normalización de fechas;
- agrupación de errores por auditor y fecha;
- resolución de nombres de auditores;
- enriquecimiento evaluaciones + detalles;
- líderes;
- transformación snake_case → camelCase de resúmenes.

## Decisiones deliberadas

### N+1

`evaluaciones-con-detalles` continúa realizando una consulta de detalles por
evaluación. Se preserva hasta que Reportes quede totalmente modularizado.

### periodo en Evolutivo

Se conserva el parámetro `periodo`, aunque todavía no modifica el dataset.

### fallos al resolver nombres

Si `usuarios` falla al buscar `nombre_completo`, el reporte no falla: usa el
nombre de usuario, igual que el comportamiento legacy.

## Qué permanece en server.js

Solo responsabilidad HTTP:

- leer query params;
- validar token cuando el handler legacy lo hacía;
- status codes;
- serialización JSON;
- logs.
